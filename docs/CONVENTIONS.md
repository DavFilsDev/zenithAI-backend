# Conventions

Rules for this repository. They apply to code and documentation alike. Anything not covered here is settled by judgement, and the decision is written down in the pull request.

## Workflow rules

### Branches

One branch per subject, named after its prefix:

| Prefix | Use |
|---|---|
| `docs/*` | Documentation only |
| `feat/*` | New behaviour |
| `fix/*` | Bug fix |
| `chore/*` | Tooling, dependencies, configuration, refactors with no behaviour change |

Examples: `docs/api-contract-v1`, `feat/streaming-sse`, `fix/refresh-blacklist`, `chore/ruff-config`.

A branch carries one subject. Unrelated changes are split into several branches, so each one can be reviewed and reverted on its own.

### Commits

- **Only the human commits.** Nothing else stages, commits, pushes, rebases, resets or stashes.
- AI coding agents never run `git add`, `git commit`, `git push`, `git reset`, `git stash`, `git checkout --`, or any history rewriting command. They edit the working tree and report what changed.
- An agent that needs a new branch asks for it, and stops there.
- Commits follow [Conventional Commits](https://www.conventionalcommits.org/): `type(scope): subject`, lowercase, imperative, no trailing period, one logical change per commit.
- Allowed types: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf`, `build`, `ci`.
- Subject line under 72 characters. The body explains the reason for the change when it is not obvious from the diff.

### The API contract

- [`docs/API_CONTRACT.md`](API_CONTRACT.md) is read **before** any change that touches the API: routes, methods, payloads, status codes, error codes, pagination, authentication, streaming.
- The contract is shared with the frontend repository. Both copies stay identical. A change lands in both, in the same release.
- Anything the contract does not describe is not part of the API yet.
- The OpenAPI schema generated by drf-spectacular describes what exists today, and never contradicts the contract without an explicit note.

### Comments

- No comment unless it explains a non-obvious *why*. Never a *what*: the code says what it does.
- No decorative comments, no section banners, no commented-out code.
- No docstrings that only restate the name of a function or class. A docstring is allowed when it explains a constraint, a non-obvious side effect, or a decision that would otherwise look wrong.
- Rules from Django, DRF or Python itself do not need to be repeated in the code.
- One line per comment, written in English, ending with a period only if it is a full sentence.

## Python and Django conventions

### Structure

```
backend/   project settings and root URLconf
users/     custom user model, registration, profile
chat/      conversations and messages
```

Inside an app, business logic never lives in a view:

| Module | Contains |
|---|---|
| `models.py` | Persistence only |
| `serializers.py` | Input and output shaping only |
| `views.py` | HTTP only: permissions, status codes, wiring |
| `services.py` | Use cases, orchestration, LLM calls |
| `selectors.py` | Read queries, always filtered by the current user |
| `permissions.py` | Reusable permission classes |

The current `chat/services.py` already follows this split for the LLM part. `selectors.py` does not exist yet, see P3 in the improvement plan.

### Serializers

- One serializer per direction. A `*Input` / `*Output` split as soon as a serializer would otherwise expose fields on write that must stay read-only, or the reverse.
- Never return a model instance or a queryset from a view. Always a serializer.
- `fields` is an explicit allow-list. `'__all__'` is forbidden: a new model field must never leak into the API by accident.
- Computed fields declare their type for the schema, and use `source=` rather than a `get_<field>` method when the value is a simple lookup.
- Nested serializers are used only when the nested set is bounded. Otherwise expose a dedicated sub-resource endpoint.

### Permissions

- The default permission is `IsAuthenticated`; the public endpoints opt out explicitly.
- Every queryset owned by a user is filtered by `request.user` in one place, in `get_queryset()` or in a selector. A view without that filter is a bug.
- Object access always goes through the filtered queryset, so an object owned by somebody else produces `404`, never `403`.
- Permissions that mix access rules and business rules are written as a `permissions.py` class, not inlined in the view.

### Views

- Generic views (`generics.*`, `APIView`) stay generic. Custom behaviour is a small method, not a copy of `ListCreateAPIView` with overridden dispatch.
- Status codes are explicit. `201` when a resource is created, `200` otherwise, `204` on delete, `400` on validation failure.
- Business failures never return a bare string body. They go through the shared error envelope, see the contract.
- Views never call an external provider directly; they call a service.

### Tests

- One test module per app: `users/tests/`, `chat/tests/`. Split by feature once a module passes a few hundred lines.
- Naming: `test_<feature>_<expected outcome>`, for example `test_list_conversations_is_scoped_to_owner`.
- Every endpoint has at least: the happy path, the unauthenticated case, the wrong-owner case, and the validation case.
- Providers are never called for real in tests. The provider interface is replaced by a fake.
- Coverage target: 85% on `users/` and `chat/`, measured, enforced in CI.

### Naming

- Modules and functions: `snake_case`. Classes: `PascalCase`. Constants: `UPPER_SNAKE_CASE`.
- Django models: singular nouns. Related names are plural, except the reverse side of a `OneToOneField`, which is singular.
- Django field names: `snake_case`, no abbreviation (`user_identifier`, not `usr_id`).
- Serializers are suffixed by role: `ConversationSerializer`, `ConversationCreateSerializer`.
- Environment variables: `UPPER_SNAKE_CASE`. Settings that map to one are declared in the same order in `.env.example`.
- Dates and timestamps in the API are ISO 8601 in UTC, with a trailing `Z`.

### Imports

- Standard library, then third party, then local, separated by a blank line.
- Absolute imports inside a project (`from chat.models import Conversation`).
- Imports are not reordered for aesthetics mid-file, only when a new import is added.

### Git and pull requests

- A pull request describes what changes for the user, and what does not change. Breaking API changes are listed explicitly.
- A pull request that changes the API updates the contract, the API documentation and the Postman collection in the same commit set.
- A pull request touching the LLM path updates the provider documentation in the improvement plan.
